Maintenance work critique

2026-11-19. Covers merged PR #238 (9f06c62e quick service + check details sheets, 7a55a851 3-pillar cockpit) and the uncommitted follow-up on main (Records screen split, forecast strip removed).

Verdict

The uncommitted follow-up is a good correction: it drops about 970 lines, the main screen answers "what's next" again, and history, costs and papers move to /home/maintenance/records. The real problems came in with PR #238. Its two new sheets, which are now the main way to log a service and to open a check, look like a demo mock-up that was merged as production code: fake default data, invented wear claims, English-only text, km only. The redesign also made several settings unreachable. Fix these before the next release, because they write wrong data into riders' service records.

Must fix (wrong data or false claims)

data

Quick Service sheet saves made-up defaults. widgets/quick_service_sheet.dart:101-107 pre-fills cost 650, workshop "Yamaha Authorized Service, Tejgaon" and oil brand "Motul 7100 10W-40". The "remembered" workshops are a hardcoded list (lines 87-92), not the rider's real remembered shops. If a rider taps Save without editing, all three are written to the visit, and from there they feed ৳/km, 12-month spend, service history and the exported PDF. The FAB and every row's ✓ button open this sheet, so this is now the default logging path.
Fix: start with these fields empty and use the shop memory that AddMaintenanceLogScreen already uses.

data

Odometer is km-only. The label is "Service Odometer (KM)", the chips are ±50/±100 km and the snackbar says "km" (lines 457-514, 297), with no imperial conversion. A rider using miles types miles and they are saved as km, and syncOdometer then also moves the bike's odometer (line 268).
Fix: convert the way AddMaintenanceLogScreen does, or reuse its field.

false claim

Check Details sheet invents wear factors. widgets/check_details_sheet.dart:304-395: when a check is not adapted, it shows hardcoded "+15% Wear: Dhaka metropolitan road dust", "+10% Wear: Aggressive acceleration profile detected on commute" and "−5% highway cruising". None of this is computed. Riders are told the app detected their riding style when it didn't, which goes against the feature's own rule (features.md: "never overdue by guesswork").
Fix: delete the else branch, or show "No adjustment for your riding".

regression

Settings were dropped and are now unreachable. 7a55a851 removed MaintenanceSettingsSection from the screen. The ⋮ menu brought back only Export, Schedule, Custom checks and Units. These have no entry point left:

  • Maintenance reminders on/off (maintenanceAlertsEnabledProvider). Riders can no longer turn off maintenance notifications.
  • Adapt to my riding switch (setAdaptIntervals).
  • Reset service log (ResetMaintenanceLogSheet).
  • Running costs settings (RunningCostsSheet, still reachable only from the ride summary cost card).

The uncommitted features.md edit doesn't list them anywhere either.
Fix: add them to the ⋮ menu, or render MaintenanceSettingsSection at the bottom of the Records screen. The second is one line and keeps the existing tested widget.

Should fix

l10n

English-only text in a bilingual app. In quick_service_sheet.dart, every section label, bundle name, date chip, oil chip, cost chip, "SNAP INVOICE"/"GALLERY" and the success snackbar is a literal. check_details_sheet.dart has the same problem ("ADAPTIVE WEAR MULTIPLIERS (THROTTLEIQ ENGINE)", "⚡ LOG THIS SERVICE", "CALIBRATE", subtitle). maintenance_screen.dart:322 has 'Units: Imperial (mi)', even though l10n.maintDistanceUnits already exists. Bangla users get a mixed-language screen.

parity

Quick Service sheet skips safeguards the full Log Visit screen has.

  • No warning when the odometer is below an earlier log (77d457e7).
  • No Undo after saving (features.md promises it).
  • "1st Free Service" is hardcoded free:1 instead of the next free service #n.
  • ShopKind is guessed from the shop name: any name containing "service" counts as authorized (lines 248-254).
  • For a multi-item visit no per-item cost is stored, so the per-part cost trends get nothing.

There are now two 800-900 line logging UIs that drift apart. Pick one: make the sheet a thin pre-filled entry into the existing screen, or move the screen's validation into a shared place.

ui

The date picker forces a dark theme (ColorScheme.dark, quick_service_sheet.dart:171), so in light mode you get a dark dialog. Buttons hardcode Colors.black on palette.primary.

ux

The CALIBRATE button can silently do nothing. In check_details_sheet.dart:460-466, when config == null it closes the sheet and opens nothing. Both buttons also call Navigator.pop() and then show(context, …) with the context of the sheet that is closing. That works only while the closing animation keeps the element mounted; capture the parent navigator or context before popping.

duplication

Two detail UIs for one check. The row opens CheckDetailsSheet (498 lines), and CheckDetailScreen (278 lines, route /home/maintenance/check) is now only a fallback for when the bike isn't loaded yet. The two show different information. Keep one of them.

Process

  • PR #238 combined a 3,000-line UI rewrite with blackbox hardware docs and deploy-script edits. Separate PRs would have made the fake data and the missing settings easy to spot in review.
  • The sheet tests check that widgets render, not what gets saved. One test that taps Save without editing and asserts that cost, shop and brand are null would have caught the worst bug here.
  • The redesign shipped and was simplified again within about a week. Before merging the next layout change, a short "what does each setting move to" list would have caught the dropped toggles.

Suggested order

  1. Remove the fake defaults and the invented wear text (small change, highest harm).
  2. Restore the settings section (one line on the Records screen).
  3. Fix imperial in the quick sheet.
  4. Localize both sheets.
  5. Decide on one logging flow and one detail UI.
