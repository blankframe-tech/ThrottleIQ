# Spark quota load test, 2026-10-15

Commit `714f8d6` (beta-v4.7.0). Runs section 3 of `../../../LOAD_TEST_PLAN.md`, which lives one level above this repo.

**Verdict: fail.** Read quota runs out first. At a rough rider-day profile, the free 50k reads a day cover about **18 daily active riders**. That is about 9 at the plan's 50% target. Two map features cause most of the cost: nearby places refetching during rides, and group-ride position fan-out.

## How it was run

- Script: `scripts/loadtest/quota_sim.js`. Run it with `npm run loadtest:quota` from `scripts/`.
- The script replays the app's real Firestore query and write shapes. It uses the JS client SDK against the Firestore emulator, with `firestore.rules` enforced. Every file and line it copies is cited in the script.
- It counts billable operations, not latency. A query costs at least 1 read. A listener costs its first result, then 1 read per changed doc.
- Rules `get()` and `exists()` calls also cost reads. The emulator does not report them, so they were added by hand from the rules. Example: a `memberLocations` write does 1 `get()` on the ride doc.
- Self-checks: every app query shape passed the rules (0 denied), and the counts matched the hand-derived formulas.
- Production was not touched.

## What drives the cost

1. **Nearby places during a ride.** `live_ride_places_provider.dart:45` fetches every place within 25 km at ride start, then again each time the rider moves 5 km. In Dhaka, 25 km covers almost all of the ~395 places plus ~90 checkposts and ~33 AI cameras. Every fetch is billed again, because a `get()` while online reads from the server. A 10 km commute makes about 2 fetches, roughly 1,000 reads.
   - This one is an estimate from the code and the seed counts. The script does not port `GeohashUtil.coverCircle`, which decides the cells.
2. **Group-ride fan-out grows with N².** Every member's map listens to the whole `memberLocations` collection. So each member's write is read once by each of the N riders, plus 1 rules `get()`. Moving the payload into one doc does not help, because each write still reaches N listeners.
3. **Feed vote lookups.** A feed page spends 40 of its 63 base reads checking whether the user voted on the 20 shown rides. That is 20 vote-doc `get()`s, each with a rules `get()` on the ride (`ride_share_repository.dart:350`).
   - Each followed rider also costs at least 3 reads per page: one query for followers-only posts plus 2 rules `exists()` checks. This applies even when that rider has no such posts.

- Reads cap: 50,000 / 2,700 ≈ **18 daily active riders** (9 at 50%).
- Writes cap: 20,000 / 89 ≈ 224 daily active riders.
- Without the places refetch, reads drop to about 640 per rider-day. That is about 78 riders (39 at 50%).

## Fixes, biggest saving first

1. **Cache places on the device.** Fetch once a day, or pull only changed docs with an `updatedAt > lastPull` query, the way sync already does. Do not refetch every 5 km. Saves about 2,000 reads per rider-day.
2. **Move group-ride positions off Firestore reads.** The RTDB relay already exists (`core/realtime/`), but `database.rules.json` denies everything (B9). RTDB bills bandwidth, not reads. The Spark tier gives 100 concurrent connections and 10 GB of downloads a month.
   - Stopgap: a 30 s interval with a 50 m move gate cuts fan-out by about a third.
   - Either way, a 20-rider ride needs one of these before it ships widely.
3. **Batch vote lookups.** Keep the user's votes in a single per-user doc, or fetch them in one query. Saves about 40 reads per feed page.
4. **Add a `hasRestrictedPosts` flag on authors.** This skips the per-author restricted query when an author has none of those posts (handoff §90.A1 already suggests it).

## Stale facts found

The handoff doc is out of date in two places:
